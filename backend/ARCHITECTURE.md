# Архитектура POVOD

Этот документ одинаков в frontend и backend-репозиториях. Обновляйте его при изменении границ компонентов, модели данных, интеграций или способа развёртывания.

## Назначение

POVOD — сервис поиска, создания и социального планирования локальных событий, рассчитанный на запуск как VK Mini App и в обычном браузере.

## Текущая схема

```text
React + Vite + VKUI
        |
        | HTTP / JSON, VITE_API_URL
        v
Express + TypeScript REST API
        |
        +-- in-memory / data/db.json
        +-- PostgreSQL (JSONB-снимок, если задан DATABASE_URL)
        +-- KudaGo Public API (концерты и фестивали)
        +-- VK launch-параметры
```

## Ответственность частей

| Часть | Ответственность |
| --- | --- |
| Frontend | UI, навигация, VK Bridge, отображение и локальное состояние. |
| Backend | API, валидация запросов, хранение данных, импорт внешних событий. |
| PostgreSQL | Постоянное хранение данных в production-режиме. |
| KudaGo | Внешний каталог публичных событий; не источник пользовательских данных. |

## Основной API-контракт

- `/api/Events` — события, создание, изменение, запись и отмена записи.
- `/api/Users` — пользователи и друзья.
- `/api/Comments` — комментарии к событиям.
- `/api/Auth/vk` — вход через launch-параметры VK.
- `/health` и `/api/ping` — служебные проверки.

## Текущие ограничения

- PostgreSQL использует единый JSONB-снимок вместо нормализованных таблиц.
- Проверка VK выполняется при авторизации, но операции изменения данных ещё не защищены серверной сессией.
- Дата события передаётся как строка для совместимости с исходным UI.
- Chat и уведомления не являются завершёнными серверными функциями.

## Правила изменений

1. Изменение API-контракта выполняется согласованно в двух репозиториях.
2. Изменение схемы хранения должно включать миграцию, обновление API и документации.
3. Новая внешняя интеграция должна иметь обработку ошибок, ограничение запросов и понятный fallback.
4. Значимое архитектурное решение фиксируется здесь и в `CHANGELOG.md`.
