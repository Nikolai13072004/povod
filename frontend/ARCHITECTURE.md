# Архитектура POVOD

Этот документ одинаков в frontend и backend-репозиториях. Обновляйте его при изменении границ компонентов, модели данных, интеграций или способа развёртывания.

## Назначение

POVOD — самостоятельный сервис поиска, создания и социального планирования локальных событий. Он полноценно работает в браузере и может подключаться к VK Mini Apps, Telegram, MAX и другим платформам через независимые адаптеры.

## Текущая схема

```text
Web / PWA      VK Mini App      Telegram / MAX / другие платформы
    \               |                         /
     \              |                        /
      +----- frontend и platform adapters ----+
                         |
                         | HTTP / JSON, VITE_API_URL
                         v
              Express + TypeScript REST API
                         |
        +----------------+-----------------+
        |                |                 |
 PostgreSQL        KudaGo Public API   провайдеры идентификации
 (основные данные) (каталог событий)  и уведомлений
```

## Ответственность частей

| Часть | Ответственность |
| --- | --- |
| Frontend | Адаптивный web/PWA UI, навигация, отображение и локальное состояние. |
| Backend | Платформенно-независимые API, аутентификация, авторизация, валидация, хранение данных и импорт внешних событий. |
| PostgreSQL | Нормализованное постоянное хранение доменных данных и применение SQL-миграций. |
| KudaGo | Внешний каталог публичных событий; не источник пользовательских данных. |
| Platform adapters | Интеграция с VK, Telegram, MAX и другими платформами: авторизация, запуск, шеринг и уведомления. |

## Принципы мультиплатформенности

1. Пользователь, событие, участие и комментарий принадлежат POVOD, а не социальной платформе.
2. Внешняя учётная запись привязывается к собственному пользователю POVOD через отдельную сущность идентичности; один пользователь может связать несколько платформ.
3. Бизнес-правила API не зависят от VK Bridge, Telegram Bot API, MAX или другого поставщика.
4. Адаптер платформы передаёт только проверенную идентичность и поддерживаемые возможности: вход, deep link, приглашение, шеринг или уведомление.
5. Доступ к друзьям, контактам и отправке уведомлений возможен только с явного согласия пользователя и при наличии официального API платформы.
6. Локальная среда разработки поднимается одной командой через Docker Compose: frontend, API и PostgreSQL.

## Основной API-контракт

- `/api/Events` — события, создание, изменение, запись и отмена записи.
- `/api/Events/author/:userId` и `/api/Events/participant/:userId` — созданные и посещаемые события пользователя.
- `/api/Users` — пользователи и друзья.
- `/api/Comments` — комментарии к событиям.
- `/api/Auth/vk` — вход через launch-параметры VK.
- `/api/Auth/register`, `/api/Auth/login`, `/api/Auth/session`, `/api/Auth/logout` — собственная браузерная учётная запись и жизненный цикл серверной сессии.
- `/health` и `/api/ping` — служебные проверки.

## Текущие ограничения

- PostgreSQL использует таблицы `users`, `events`, `event_participants`, `comments`, `friendships`, `password_credentials`, `external_identities` и `auth_sessions`; изменения схемы применяются нумерованными SQL-миграциями.
- При первом запуске на существующей базе содержимое прежнего `app_snapshot` идемпотентно импортируется в нормализованные таблицы. Сам снимок не удаляется автоматически.
- Backend обращается к данным через асинхронный интерфейс репозитория с адаптерами PostgreSQL и in-memory/JSON для локальной разработки.
- Пароли хранятся отдельно от пользователя как `scrypt`-хэши; непрозрачный токен сессии показывается только клиенту, а в базе хранится его SHA-256-хэш. Сессия имеет срок действия и может быть отозвана.
- Browser/PWA хранит токен в `sessionStorage` и передаёт его в `Authorization: Bearer`; защищённые страницы требуют подтверждённую сервером сессию.
- Автор события и комментария всегда определяется сервером. Изменение и удаление события разрешено его автору; удаление комментария — автору комментария или события.
- Приватные события и их комментарии доступны только автору и участникам.
- VK связан с собственным пользователем POVOD через `external_identities`; в production вход VK отключается, если не настроена проверка подписи.
- В PostgreSQL начало события хранится как `TIMESTAMPTZ`; API временно продолжает отдавать отдельные `date` и `time` для совместимости с исходным UI.
- Chat и уведомления не являются завершёнными серверными функциями.
- Адаптеры Telegram, MAX и других платформ пока не реализованы; их контракт определяется только после проверки официальных API и правил площадки.
- Ограничение частоты входа пока хранится в памяти одного процесса; для горизонтального масштабирования потребуется общий rate-limit store.

## Правила изменений

1. Изменение API-контракта выполняется согласованно в двух репозиториях.
2. Изменение схемы хранения должно включать новую обратимо-безопасную миграцию, обновление репозитория, тестов и документации; уже применённые миграции не редактируются.
3. Новая внешняя интеграция должна иметь обработку ошибок, ограничение запросов и понятный fallback.
4. Значимое архитектурное решение фиксируется здесь и в `CHANGELOG.md`.
